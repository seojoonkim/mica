# standard-v1.3.4 공정 보완안

## 1. 적용 시점

이 문서는 진행 중인 `std-b11`에 소급 적용하지 않는다. `std-b11`을 현재 잠금으로 종결하고 Codex가 종료 증거를 검토한 뒤, 다음 빈 배치 경계에서만 방법 revision과 검증기를 변경한다.

## 2. std-b11에서 확인된 결함

### P0. source review가 범위를 넘는 한계 서술을 수락함

`ev-b11-02.limitations`의 일부 인과 서술은 원문에 없다고 독립 검토자가 확인했다. 그러나 source review 검사 키에 `limitationsHonesty`가 없어서 `sr-b11-02`는 `accept`로 남았다. 이는 자료가 범위를 넘는 주장을 포함하면 reject한다는 역할 계약과 충돌한다.

### P1. controller 저작 산출물을 원장에 기록할 명령이 없음

`resume`은 비어 있지 않은 JSON과 JSONL을 `artifactShaLedger`와 대조한다. 그러나 `defect-ledger.jsonl`처럼 controller가 직접 작성하는 산출물은 `complete-role`에 귀속할 수 없어 정식 원장 기록 경로가 없다. 그 결과 결함을 기록한 배치가 lease 만료 후 스스로 재개되지 못했다.

### P1. 역할 선점과 쓰기 승인 사이의 순서가 기계적으로 결속되지 않음

controller가 `assign-role` 결과를 확인하기 전에 쓰기 승인 메시지를 보낼 수 있다. `std-b11`에서는 lease 만료 때문에 선점이 실패했지만 승인이 먼저 전달됐다. 실제 파일 쓰기는 철회로 막았으나, 현재 계약은 이 경쟁 상태를 기계적으로 차단하지 못한다.

### P2. 역할 브리핑의 스키마 개수를 사람이 다시 세어 적음

source evidence 필드는 13개인데 브리핑에는 12개라고 표기됐다. 역할이 나열된 13개 필드를 따라 결과는 정상으로 남았지만, 다음 실행에서는 필드 누락을 만들 수 있다.

### P2. 90분 lease가 긴 역할 실행과 세션 전환에 짧음

source 검토와 다음 역할 사이의 유휴 구간에서 lease가 만료됐다. 만료 자체는 정상적인 안전 동작이지만, 경고나 명시적 park 없이 만료되면 복구 비용과 승인 경쟁 상태가 커진다.

## 3. v1.3.4 필수 변경

### 3.1 source review 최소 검사 집합을 계약으로 고정

검사 키는 다음 순서를 고정한다.

1. `publisher`
2. `scope`
3. `verbatim`
4. `directSupport`
5. `typeAccuracy`
6. `recency`
7. `limitationsHonesty`

모든 값은 `pass` 또는 `fail`만 허용한다. 하나라도 `fail`이면 `verdict=reject`여야 한다. `limitationsHonesty`는 다음을 확인한다.

- 원문에 없는 인과, 일반화, 분모 결합을 한계 설명에 넣지 않았는가
- 자료가 다루지 않은 인구, 시장, 기간, 절차를 다룬 것처럼 쓰지 않았는가
- 오래된 자료의 현재 유효성을 별도 근거 없이 현재형으로 확정하지 않았는가

검증기는 source review exact key 집합, 값 enum, all-pass와 verdict의 정합성을 검사한다.

### 3.2 controller용 `record-artifact` 명령 추가

다음 명령을 추가한다.

```bash
python3 scripts/mica-batch-control.py record-artifact \
  work/mica-scenario-batches/<batch-id> \
  --controller-context-id <controller-id> \
  --session-id <session-id> \
  --artifact defect-ledger.jsonl
```

요구 조건:

- 활성 controller lease를 통과해야 한다.
- 상대경로만 허용하고 배치 밖 경로, `controller-state.json`, `batch-manifest.json`은 거절한다.
- controller 소유 허용 목록은 `defect-ledger.jsonl`, `closure.json`으로 시작한다.
- SHA-256, 파일 mtime, controller 관측 시각, `closedBy=controllerContextId`, `timeSource=filesystem-mtime-observed-by-controller-tool`을 기록한다.
- 같은 path는 upsert하고 다른 원장 행은 보존한다.

`resume`은 기존 전수 결속 검사를 유지한다. `defect-ledger.jsonl`을 단순 예외 처리하지 않는다.

### 3.3 역할 쓰기 승인 영수증 추가

`assign-role` PASS 뒤 반환값에 아래 필드를 포함한다.

- `role`
- `roleContextId`
- `generation`
- `claimRecordedAt`
- `leaseExpiresAt`
- `writeAuthorizationToken`

token은 배치 ID, generation, role, context ID, claim 시각을 정규화해 SHA-256으로 만든다. 역할 브리핑에는 이 token을 포함하고, 역할 완료 시 `complete-role --write-authorization-token`으로 다시 제출한다.

controller 순서는 다음으로 고정한다.

1. lease 상태 확인 또는 renew
2. `assign-role` 실행
3. PASS와 token 확인
4. 역할에 쓰기 승인 전달
5. 역할 산출물 종료
6. token을 포함해 `complete-role`

선점 전 승인 메시지는 계약상 효력이 없다.

### 3.4 역할 브리핑을 기계 생성

역할별 exact key 목록과 허용 입력, 출력 path는 단일 schema source에서 생성한다. controller가 키 개수를 자연어로 다시 적지 않는다. 사람용 브리핑에는 개수 대신 생성된 필드 목록과 schema version을 넣는다.

### 3.5 lease 운영 보완

- standard 프로필 기본 TTL을 180분으로 바꾼다.
- 30분 이상 유휴가 예상되면 `park`를 먼저 실행한다.
- 역할 시작 전 잔여 시간이 30분 미만이면 `renew` 뒤 `assign-role`을 실행한다.
- TTL 연장은 안전 경계를 약화하지 않는다. 만료 후에는 기존처럼 사용자 승인 ref가 있는 `resume`만 허용한다.

## 4. 회귀 검사

다음 시나리오가 모두 통과해야 v1.3.4를 다음 배치에 사용할 수 있다.

1. source review에서 `limitationsHonesty=fail`, `verdict=accept`를 거절한다.
2. source review에서 검사 키가 빠지거나 추가되면 거절한다.
3. 원문에 없는 인과를 발견한 source row는 reject되고 accepted-only 입력에서 제외된다.
4. `record-artifact`가 defect ledger를 원장화한 뒤 lease 만료와 승인된 resume이 통과한다.
5. 원장화 후 defect ledger 바이트가 바뀌면 resume이 실패한다.
6. 배치 밖 path, 상태 파일, manifest를 `record-artifact`로 기록하려 하면 실패한다.
7. 만료된 lease에서 `assign-role`이 실패하면 token이 발급되지 않는다.
8. 다른 generation, role, context ID의 token으로 `complete-role`을 실행하면 실패한다.
9. 정상 선점, 작성, 완료 경로는 기존 artifact SHA와 model record를 보존한다.
10. park, resume, controller transfer 뒤 이전 generation의 token은 실패한다.

## 5. std-b11 종결 전 별도 조치

방법 파일을 바꾸지 않고 source gate만 계약에 맞게 닫는다.

- `sr-b11-02`를 reject로 정정하고 해당 evidence를 downstream accepted 집합에서 제외하거나,
- source researcher, need writer와 다른 새 독립 reviewer context가 원문과 계약을 다시 대조해 별도 판정을 기록한다.

원문 `source-evidence.jsonl`은 수정하지 않는다. 같은 배치에서 새 evidence ID로 재작성하지 않는다. 이미 need writer가 시작됐다면 `ev-b11-02`의 원문에 없는 인과와 혼합 분모가 downstream 산출물에 들어갔는지 별도 대조한다.

## 6. 완료 정의

다음 조건을 모두 충족할 때 v1.3.4 제안을 구현 완료로 본다.

- source review 의미 계약과 기계 검증이 같은 검사 집합을 사용한다.
- controller 산출물이 예외 없이 SHA 원장에 결속된다.
- 역할 선점 PASS 전에는 유효한 쓰기 승인 token이 존재하지 않는다.
- 브리핑 스키마가 코드에서 생성된다.
- 위 회귀 검사와 기존 생산, controller 테스트가 모두 통과한다.
- 빈 시험 배치에서 claim, assign, complete, park, resume, close 대표 흐름을 실제 CLI로 확인한다.
