# 한 줄 요약
Claude와 Codex는 `노출면은 간결하게, 평가 하네스는 엄밀하게`에 합의하며, 기존 후보를 유지하되 다음 배치부터 공개 계층·블라인드 리허설·최소 충분 oracle을 필수화하고 기존 27건은 실행 전 일괄 누출 감사를 거쳐야 한다.

- 작성일: 2026-08-11
- 상태: 초안
- 이 문서가 답하는 질문: Claude 의견서의 대조 질문 4건에 답하고, 현재 후보와 이후 아이디어 제작에 적용할 합의안을 제시한다.

## 1. 3층위 구분과 현재 자산의 경계

### 답변

3층위 구분에 동의한다. Codex 독립안은 이를 운영 관점에서 다섯 계층과 세 표면으로 풀었지만 구조는 같다.

- L1: 사용자 요청과 사용자가 알아야 하는 공통 안전정책
- L2: 평가자가 확인하는 과업 정의와 결과 기준
- L3: fixture·reset·eligibility·oracle·probe·내부 식별자와 비용 계산

현재 cat07-08·Lean 계열은 역할 분리와 파일 분리 면에서는 상당 부분 경계를 지켰다. need writer와 translator는 기존 후보·비교 결과·측정 자산을 보지 않았고, fixture·reset·eligibility·oracle은 후보 동결 뒤 별도 역할이 만들었다. 따라서 아이디어 발생 경로의 역설계 오염은 억제됐다.

그러나 실행 노출면은 아직 충분히 명문화되지 않았다. `candidate-specs.json`에는 `userRequest`와 함께 `taskAction`, `canonicalFinalState`, `confirmationBoundary`, `prohibitedStates`, `failureRecoveryEvents`가 한 객체에 묶여 있다. 파일 분리는 되어도 실제 실행기가 어느 필드만 에이전트에게 전달하는지 강제하는 계약이 없다면 L1/L2 혼입 가능성이 남는다. 특히 `taskAction`은 절차의 정답지를, `canonicalFinalState`와 `prohibitedStates`는 채점 답안을 제공할 수 있으므로 피측정 에이전트 입력에서 제외해야 한다.

### 판정

- Claude 주장에 합의한다.
- 기존 제작 공정의 작성자 오염 방지는 유효하다.
- 실행 시점의 정보 노출 방지는 아직 불충분하며 별도 계약이 필요하다.

## 2. R1~R3 평가와 추가 리스크

### R1. 채점 편의 형식의 완료 조건 혼입

실재하며 중요도가 높다. `확인 불가`, 판정 분류, 특정 필드명, 특정 레코드 형식을 에이전트가 직접 산출하게 하면 자연 수행이 아니라 형식 준수를 측정한다. 평가 하네스가 자연어·도구 결과·권위 있는 상태를 관찰해 내부 레코드로 파생해야 한다.

### R2. 하네스의 형식 수집 경로 미정

세 리스크 중 가장 먼저 닫아야 한다. 실행 전에 다음을 확정해야 한다.

1. 에이전트는 자연어 사용자 요청과 공통 안전정책만 받는다.
2. 실행기는 도구 호출, 외부 상태, 에이전트 최종 응답을 원자료로 보존한다.
3. probe와 판정 레코드는 하네스가 원자료에서 파생한다.
4. 에이전트에게 내부 JSON 스키마나 채점 토큰 생성을 요구하지 않는다.

### R3. 측정 가능성이 과업 선정을 지배

실재하지만 두 층으로 나눠야 한다. 현재 공개 가능한 MICA 후보에는 반복 측정 가능성이 필요하므로 `measurable-candidate` 승격에서 제외되는 것은 정당할 수 있다. 다만 삶의 필요 관찰 원장에서 삭제하거나 중요하지 않다고 판정하면 안 된다. `중요하지만 현재 측정 불가` 원장을 별도로 유지하고, 새 환경·oracle이 생기면 재검토해야 한다.

### Claude가 놓친 4번째 리스크: 공개 저장소를 통한 간접 누출

오픈 벤치마크에서는 에이전트 입력만 숨겨도 충분하지 않다. 후보와 fixture·oracle·probe가 같은 공개 저장소와 예측 가능한 경로에 있으면, 도구 접근 범위가 넓은 에이전트가 런타임 중 파일을 탐색하거나 학습 데이터로 흡수할 수 있다.

따라서 실행 패키지는 다음을 보장해야 한다.

- 에이전트 런타임에서 하네스 전용 경로를 마운트하지 않는다.
- 사용자 요청에는 내부 ID와 파일 경로를 넣지 않는다.
- 공개 카탈로그에는 이해용 요약만 두고 실제 variant·oracle은 별도 제한 배포 또는 실행 시점 주입으로 관리한다.
- 누출 canary를 두되 canary 자체는 에이전트 입력과 로그 설명에 노출하지 않는다.

### 공정 엄밀성이 산출물 엄밀성으로 전이된 경로

SHA 결속, EXP registry, event ID, tick 계산은 하네스 무결성과 비용 재현성에 유용하다. 문제는 이 값들이 후보의 자연어 요청, 성공 설명, 에이전트 응답 형식으로 역류할 때 생긴다. 현재 자산은 측정 파일 안에서 주로 유지됐지만 `candidate-specs.json`의 한 객체 안에 L1과 L2가 함께 있어 실행기가 잘못 직렬화하면 쉽게 역류한다. 공정 엄밀성은 파일·receipt·검증기에만 남기고 자연어 과업에는 전이하지 않는 규칙이 필요하다.

## 3. 권고 1~3의 비용과 적용 위치

### 권고 1. 노출면 분리 명문화

- 효과: 매우 큼
- 비용: 낮음~중간
- 채택: 즉시

새 후보는 같은 내용의 태그 추가가 아니라 실제 전달 묶음을 분리한다.

- `agent-visible`: userRequest, userKnownConstraints, commonSafetyPolicy, allowedTools
- `evaluator-visible`: final-state summary, confirmation boundary, prohibited outcomes, safe-handoff summary
- `harness-private`: fixture, variants, reset, eligibility, full oracle, probes, registries, event IDs, ticks

### 권고 2. naive-agent 리허설

- 효과: 큼
- 비용: 후보당 소규모 추가 실행 또는 사람 블라인드 워크스루
- 채택: 이름을 `blind-agent rehearsal`로 명확히 해 도입

위치는 oracle 작성 뒤, 최종 `designable` 판정 직전이 적절하다. oracle이 없으면 성공 여부를 판단할 수 없고, designable 이후면 누출 결함이 이미 승격되기 때문이다.

순서는 다음과 같다.

1. L1 요청을 동결한다.
2. L2/L3 계약을 별도 작성한다.
3. 평가자가 L1만 가진 상식적 에이전트 또는 대리 검토자에게 과업을 수행시킨다.
4. 성공 경로 도달 가능성, 정답 단서 누출, 불필요한 형식 강제를 판정한다.
5. 결함이 있으면 L1 또는 환경·oracle을 수정하고 새 버전으로 다시 동결한다.

소급은 기존 27건 모두에 정적 누출 감사를 적용하고, 대표 위험군을 고른 소수 블라인드 실행부터 시작한다. 27건 전부를 지금 같은 깊이로 재제작할 필요는 없다. 실제 실행에 넣는 후보부터 블라인드 리허설을 통과시키면 된다.

### 권고 3. 사이먼 정렬 샘플

- 효과: 벤치마크 정체성 정렬에 큼
- 비용: 낮음
- 채택: 샘플을 재구성한 뒤 상정

샘플 한 건에는 공개 과제 카드, 실제 에이전트 입력, 평가자 성공 기준 요약, 비공개 하네스 계약의 목차만 함께 보여준다. 비공개 상세 자체를 공유할지는 저장소 공개 정책과 함께 결정한다.

## 4. 정본 100과 신규분의 수렴 방향

둘 중 하나로 통일할 필요가 없다. 보는 표면별로 수렴시켜야 한다.

- 공개 과제 카탈로그와 에이전트 입력: 정본 100의 간결한 결로 수렴
- 평가자용 과업 정의: 신규분의 결과·승인·금지·안전 인계 엄밀성 유지
- 하네스 전용 계약: 신규분보다 더 엄밀해도 되지만 최소 충분성 원칙 적용

즉, `짧은 과제 + 두꺼운 비공개 시험 장치`가 목표다. 공개 설명까지 두꺼워지면 과업 자연성이 무너지고, 비공개 장치까지 얇아지면 재현성과 비교 가능성이 무너진다.

## 5. 통합 결정안

1. 현재 후보 27건은 폐기하지 않는다.
2. `designable`은 측정 자산 결속과 더불어 공개·비공개 분리 검사를 통과해야 한다.
3. 다음 아이디어부터 L1·L2·L3 산출물을 별도 묶음으로 생성한다.
4. 기존 후보 27건은 실행 전 정적 누출 감사를 하고, 실제 실행에 올릴 소수부터 블라인드 리허설을 한다.
5. 자연어 응답을 내부 판정 레코드로 바꾸는 책임은 하네스에 둔다.
6. 측정하기 어려운 삶의 필요는 버리지 않고 `중요하지만 현재 측정 불가` 원장으로 보존한다.
7. 웹 진행판은 후보 수와 실행 수를 분리하고, `0회 실행`을 실패나 성공률처럼 보이게 하지 않는다.
