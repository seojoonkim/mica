# standard-v1.3.5 최종 수렴 결정

## 0. 최종 판정

Claude Code의 좁은 `MODIFY`를 전부 수용한다. O1·O2·O3와 추가 회귀 2건을 아래처럼 확정한다.

이 문서가 `standard-v1.3.5` 구현 방향의 최신 기준이다. 앞선 방향 문서는 판단 이력으로 보존하고, 충돌하면 이 문서가 우선한다.

구현은 아직 시작하지 않는다. `std-b12`가 현 revision으로 종결되고 다음 조건을 모두 통과한 뒤 시작한다.

1. `closure.json` 작성
2. `validate-exposure` PASS
3. `validate-batch` PASS
4. `mica-batch-control.py close` 완료

## 1. 공식 100과 연구 포트폴리오 100

두 집합은 병존한다.

### 공식 canonical 100

- Simon이 관리하는 공식 public candidate catalogue
- 10 task family x 10 definition
- 현재 lifecycle은 전건 candidate
- validated 0건

### 신기헌 아이데이션 연구 포트폴리오 100

- 공식 이름: `kiheon-ideation 100-slot research portfolio`
- 한국어 표시: `신기헌 아이데이션 100-slot 연구 포트폴리오`
- 공식과 같은 10 category x 10 slot
- 100개 slot 전부가 `occupied`일 때만 연구 포트폴리오 완성
- 공식 canonical catalogue가 아님
- 공식 채택이나 교체는 별도 governance decision

## 2. O1 결정: 저장 위치와 원장 기록

### 2.1 repo-level 정본 경로

배치를 가로지르는 포트폴리오 정본은 배치 디렉터리 밖에 둔다.

```text
work/mica-scenario-portfolio/
  portfolio-100.json
  catalog-annotations.jsonl
  catalog-annotation-reviews.jsonl
  portfolio-artifact-ledger.jsonl
  receipts/
    <transaction-id>.json
```

이 경로에는 public research portfolio 자료만 둔다. private holdout은 이 경로에 둘 수 없다.

배치 밖에 두는 이유:

- 여러 배치의 누적 상태다.
- parked batch의 `_validate_recorded_artifacts` 대상이 되지 않는다.
- batch resume을 repo-level 원장 변경으로 차단하지 않는다.
- 공식 canonical catalogue와 별도 namespace를 유지한다.

### 2.2 per-batch staging 경로

각 신규 배치는 다음 staging 산출물만 자기 디렉터리에 둔다.

```text
work/mica-scenario-batches/<batch-id>/catalog-annotations.staging.jsonl
work/mica-scenario-batches/<batch-id>/catalog-annotation-reviews.staging.jsonl
```

두 파일은 정식 역할 산출물이다.

- `catalogAnnotator`가 첫 파일을 쓴다.
- `catalogAnnotationReviewer`가 두 번째 파일을 쓴다.
- 두 파일은 `complete-role`을 통해 batch `artifactShaLedger`에 기록한다.
- park·resume·close validator가 다른 역할 산출물과 같은 방식으로 검사한다.

### 2.3 portfolio apply transaction

배치가 완전히 닫힌 뒤에만 deterministic 명령 `portfolio-apply`가 accepted staging 행을 repo-level 정본에 병합한다.

`portfolio-apply`는 의미 판정을 하지 않는다. 다음을 기계적으로 확인한다.

1. source batch가 closed인가
2. closure·validate receipt가 유효한가
3. frozen candidate raw-row SHA가 annotation과 일치하는가
4. annotation reviewer가 accept했는가
5. annotator·reviewer context가 서로 다르고 다른 역할과 충돌하지 않는가
6. candidate가 다른 slot을 이미 점유하지 않았는가
7. target slot이 empty 또는 동일 candidate의 idempotent replay인가
8. holdout artifact가 포함되지 않았는가

성공하면 다음 receipt를 만든다.

```text
work/mica-scenario-portfolio/receipts/<transaction-id>.json
```

receipt와 `portfolio-artifact-ledger.jsonl` 행은 다음을 기록한다.

- transactionId
- sourceBatchId
- sourceClosureSha256
- staging annotation path·SHA-256
- staging review path·SHA-256
- 이전·이후 `portfolio-100.json` SHA-256
- 이전·이후 annotation ledger SHA-256
- 이전·이후 annotation review ledger SHA-256
- appliedByContextId
- observedAt
- source commit SHA

`portfolio-artifact-ledger.jsonl`은 자기 자신의 SHA를 행 안에 기록하지 않는다. 파일 자체의 버전은 git commit과 transaction receipt가 결속한다.

### 2.4 원장 변경 경계

- production agent가 repo-level 정본을 직접 수정하지 않는다.
- controller가 JSON을 손으로 병합하지 않는다.
- closed batch의 accepted staging만 `portfolio-apply`가 반영한다.
- 실패한 transaction은 repo-level 정본을 바꾸지 않는다.
- 같은 transaction의 재실행은 byte-identical idempotent result만 허용한다.

## 3. O2 결정: 정식 역할 추가

다음 두 역할을 `batch-manifest.json`, role enum, role input allowlist, output contract, assign·complete 흐름에 추가한다.

### `catalogAnnotator`

허용 입력:

- accepted frozen candidate raw rows
- 공식 task surface·termination·complexity enum 정의
- batch category target metadata
- frozen candidate raw-row SHA

금지 입력:

- annotation review 결과
- slot occupancy 정답
- private holdout
- 작성자 대화 요약

출력:

- `catalog-annotations.staging.jsonl`

### `catalogAnnotationReviewer`

허용 입력:

- accepted frozen candidate raw rows
- `catalog-annotations.staging.jsonl`
- 공식 enum과 annotation contract

금지 입력:

- annotator 대화 요약과 의도
- private holdout
- controller의 기대 판정

출력:

- `catalog-annotation-reviews.staging.jsonl`

### 역할 독립성

- 두 역할은 서로 다른 context ID를 사용한다.
- translator, candidate reviewer, candidate custodian, comparator, measurement 역할과 context ID를 재사용하지 않는다.
- `assign-role`은 기존과 같은 authorization token을 발급한다.
- `complete-role`은 토큰·context·role·mtime·artifact SHA를 결속한다.
- 역할 목록 밖 임의 context의 staging 파일은 채택하지 않는다.

## 4. annotation 구조

annotation은 frozen candidate 원문을 수정하지 않는다.

필수 항목:

- origin
- schemaVersion
- batchId
- candidateId
- sourceFrozenRowSha256
- categoryId
- proposedSlotId
- terminationClass
- declaredComplexity
- targetSurface
- surfaceStatus: `target-only`
- annotatorContextId
- annotatedAt

review 필수 항목:

- annotation raw-row SHA-256
- candidate binding 판정
- category·slot 판정
- terminationClass 판정
- declaredComplexity 판정
- targetSurface가 provisional이라는 판정
- reviewerContextId
- verdict
- reviewNote
- reviewedAt

`confirmedSurface`는 이 단계에 존재하면 안 된다.

## 5. surface 전이 규칙

### target surface

`targetSurface`는 portfolio balance와 다음 batch planning을 위한 provisional 값이다. 작성자에게는 권고로만 제공하며, 근거가 다른 실제 부담을 지지하면 불일치를 기록하고 수락할 수 있다.

### confirmed surface

다음이 모두 있어야 별도 market integration transaction에서 `confirmedSurface`를 만든다.

- representativePlatformRef
- accountTierRef
- grantedPermissionsRef
- initialStateRef
- confirmationBoundaryRef
- accessParityReviewRef
- independentMarketReviewerContextId
- confirmedAt

`targetSurface` 값과 같더라도 위 근거 없이 복사하거나 자동 승격할 수 없다.

## 6. blocked slot의 시도 이력

`blocked(evidence-insufficient)`는 완료가 아니다. 100개 완성 수량에 포함하지 않는다.

blocked 전환에는 비어 있지 않은 `attemptHistory`가 필요하다. 각 항목은 다음을 기록한다.

- batchId
- targetBriefSha256
- categoryId
- neutralSubdomain
- sourcePoolRefs
- targetSurface
- targetTerminationClass
- targetComplexity
- outcome: `reject`, `duplicate`, `hold`, `zero-evidence`
- reasonCode
- evidenceRefs
- recordedAt

동일 `targetBriefSha256`를 새 시도로 다시 사용할 수 없다. blocked slot을 다시 empty로 열 때는 새로운 source pool, neutral subdomain 또는 target metadata 중 하나 이상이 바뀌어야 하며 reopen reason을 남긴다.

## 7. O3 결정: 진행판과 공개 export

### 7.1 source of truth

진행판의 10 x 10 board와 50/100 같은 포트폴리오 수치는 batch directory scan으로 계산하지 않는다.

다음 파일만 읽는다.

```text
work/mica-scenario-portfolio/portfolio-100.json
```

상세 후보 레지스터는 closed batch 산출물을 추가로 읽을 수 있지만, slot 점유 수와 category별 완성 수는 반드시 portfolio ledger에서 계산한다.

portfolio ledger가 없거나 검증에 실패하면 과거 batch scan으로 fallback하지 않고 생성을 중단한다.

### 7.2 필수 공개 명칭

진행판과 연구 포트폴리오 export는 다음을 표시한다.

- `신기헌 아이데이션 100-slot 연구 포트폴리오`
- `공식 MICA canonical catalogue와 병존하는 비정본 연구 포트폴리오`
- `canonicalAdoptionStatus: not-adopted`

`MICA 100`, `canonical 100`, `공식 100`처럼 오독되는 단독 표현을 사용하지 않는다.

### 7.3 export namespace

연구 포트폴리오는 공식 canonical `export:data`에 자동 병합하지 않는다. 별도 `export-portfolio` 경로와 별도 파일 namespace를 사용한다.

export는 다음을 포함한다.

- portfolioId
- displayNameKo
- displayNameEn
- relationToCanonical: `parallel-research-portfolio`
- canonicalAdoptionStatus: `not-adopted`
- targetSlotCount: 100
- occupiedSlotCount
- blockedSlotCount
- category별 slot 상태
- public exposure status
- source portfolio ledger SHA-256

holdout artifact 또는 `taskSet=holdout`이 발견되면 export와 site build를 모두 차단한다.

## 8. expected diagnostic axes

measurement contract는 공식 7종 enum의 `expectedDiagnosticAxes`를 가질 수 있다. 이는 실행 전 예상 진단 범위이며 실제 coverage가 아니다.

- 빈 배열은 허용하지 않는다.
- 공식 enum 밖 자유서술 값을 거부한다.
- 실행 전 `observedDiagnosticAxes`를 생성하지 않는다.
- 실제 system attempt 뒤 별도 evidence contract가 관찰 축을 기록한다.

## 8.1 std-b12 종결 전 격차 재계수와 구현 우선순위

`std-b12` 중간 점검에서 다음 격차를 확인했다.

- `std-b12`의 frozen candidate는 2건이다.
- 이를 포함한 배치 계열 frozen candidate는 41건이다.
- 41건의 `surface`, `terminationClass`, `declaredComplexity`, `diagnosticAxes`, `marketApplicability` 결속은 각각 0건이다.
- 파일럿 15건과 배치 계열 41건을 합치면, v1.3.5 annotation 대상은 현재 56건으로 예상된다.

56건은 `std-b12`가 정상 종결되고 closure에서 frozen candidate 2건이 확인될 때 확정한다. 측정 review가 한 후보를 reject하더라도 frozen candidate 계보와 annotation 대상에서 자동 삭제하지 않는다. 측정 가능성 판정과 candidate annotation은 서로 다른 상태 축이다.

v1.3.5 구현은 다음 순서를 따른다.

1. O1의 repo-level ledger, staging, receipt, `portfolio-apply` 경계를 구현한다.
2. O2의 `catalogAnnotator`와 `catalogAnnotationReviewer` 역할, context 충돌 검사를 구현한다.
3. 종결된 공개 후보 전수에 대해 immutable annotation을 작성하고 독립 review한다. 현재 예상 대상은 56건이며 closure에서 확정한다.
4. O3의 진행판 source 전환, 공식 명칭, 별도 export namespace, no-fallback 규칙을 구현한다.
5. measurement contract의 `expectedDiagnosticAxes`와 이후 market integration의 `confirmedSurface` 경계를 구현한다.
6. future private holdout 저장·내보내기 분리를 구현하고 public 경로 도달을 fail-closed로 차단한다.

측정 자산과 oracle의 깊이는 합성 실행 재현성과 판정 가능성을 위한 별도 품질 축이다. 상세 variant, oracle 조건, 내부 issue 수가 많다는 사실만으로 공식 방법론 정합성이 충족되지는 않는다. v1.3.5 착수에서는 하네스 깊이 확장보다 위 다섯 필드의 결속, 역할 독립성, portfolio namespace, holdout 분리를 우선한다.

## 9. v1.3.5 회귀 검사

최소 회귀는 다음을 포함한다.

1. slot ledger의 정확히 10 category x 10 slot 검사
2. 한 candidate의 중복 slot 점유 거부
3. `blocked`를 occupied count에 포함하는 집계 거부
4. blocked slot의 빈 attemptHistory 거부
5. 동일 targetBriefSha256 재시도 거부
6. annotation의 잘못된 enum 거부
7. annotator·reviewer context 충돌 거부
8. annotation role context와 다른 semantic role context 재사용 거부
9. frozen candidate raw-row SHA 불일치 거부
10. review되지 않은 annotation의 portfolio apply 거부
11. closed가 아닌 batch의 portfolio apply 거부
12. `targetSurface`를 근거 없이 `confirmedSurface`로 자동 승격하는 행위 거부
13. confirmedSurface의 platform·access parity 근거 누락 거부
14. holdout public export·site build 거부
15. portfolio ledger 실패 시 batch scan fallback 거부
16. 진행판·export의 공식 포트폴리오 명칭 누락 거부
17. official canonical export와 research portfolio namespace 혼합 거부

## 10. 구현 착수 조건

다음이 모두 충족되면 Codex가 구현을 시작한다.

1. `std-b12` closure 작성
2. `std-b12` validate-exposure PASS
3. `std-b12` validate-batch PASS
4. `std-b12` close 완료
5. 이 문서가 최신 수렴 기준으로 확인됨

그 전에는 다음을 하지 않는다.

- 방법·검증기 구현
- portfolio ledger 생성
- `std-b12` 종결 수량을 포함한 공개 후보 전수 annotation 실행. 현재 예상 56건이며 closure에서 확정한다.
- 진행판 데이터 source 전환
- 새 생산 배치 생성
- 공식 canonical 100 변경
- private holdout 저작

## 11. std-b12 재개 지시

Claude Code는 현재 parked checkpoint를 먼저 검증한 뒤 `std-b12`를 `standard-v1.3.4`로 comparator부터 재개한다.

- v1.3.5 필드와 역할을 std-b12에 추가하지 않는다.
- comparator·measurement·exposure·closure를 현 lock으로 완료한다.
- v1.3.4가 발견한 결함과 v1.3.5 미적용 사실을 closure에 기록한다.
- 종결 뒤 산출물 수량, 결함, validate 결과, close 상태를 인수인계 문서로 보고한다.

## 12. 소통 규칙

이후에도 다음 형식을 유지한다.

1. 상세 판단과 실행 결과는 `work/method-reviews/`의 자족적 인수인계 문서로 남긴다.
2. 상대 런타임에는 문서 경로와 짧은 실행 메시지만 전달한다.
3. 각 문서는 근거, 판정, 적용 범위, 금지 범위, 다음 행동, 검증 결과를 포함한다.
4. 진행 중 배치에는 새 revision을 소급하지 않는다.
5. 외부 반영, commit, push는 기헌의 별도 지시가 있을 때만 한다.
