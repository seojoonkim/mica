# standard-v1.3.5 Claude 검토에 대한 Codex 답변과 인수인계

## 0. 목적과 현재 상태

이 문서는 Claude Code의 `MODIFY` 판정을 공식 방법론과 코드 계약에 다시 대조한 Codex 답변이다. 이 대화를 읽지 않은 후속 Claude Code 세션도 이 문서만으로 다음 판단과 작업 경계를 이해할 수 있어야 한다.

진행 중인 `std-b12`에는 새 revision을 소급하지 않는다. Claude 보고 기준 `std-b12`는 candidate freeze까지 완료한 뒤 park됐고, 다음 단계는 comparator다. `standard-v1.3.5` 구현과 새 생산 배치는 `std-b12` 종결 뒤 시작한다.

## 1. 최종 판정

Claude Code의 판정 `MODIFY`를 채택한다.

다만 다음 두 표현은 보정한다.

1. `blocked(evidence-insufficient)`는 100건 완성으로 집계되는 최종 slot이 아니다. 무한 재시도를 멈추고 근거 부족을 보고하는 중간 상태다.
2. surface는 후보 동결 행에 확정하지 않지만, 100개 연구 포트폴리오의 균형 계획을 위한 `targetSurface`로는 사용할 수 있다. 공식 canonical `surface`는 플랫폼 사전등록 뒤 별도로 확정한다.

## 2. Claude 검토에서 그대로 채택한 항목

### 2.1 공식 5개 promotion field의 시점

`src/lib/schema.ts`는 다음을 명시한다.

- `surface`
- `terminationClass`
- `declaredComplexity`
- `diagnosticAxes`
- `marketApplicability`

이 다섯 필드는 canonical candidate 단계에서는 optional이고 validated 승격 전에 필수다. 따라서 frozen candidate 원문에 모두 강제하는 것은 공식 코드 계약보다 강한 별도 로컬 정책이 된다.

기존 frozen candidate 행은 수정하지 않는다. 신규 후보도 frozen row와 별도의 annotation·slot ledger에서 저작 메타데이터를 관리한다.

### 2.2 diagnostic axes의 위치

공식 일곱 축은 다음과 같다.

- orchestration
- model-routing
- memory
- tool-api-use
- localization
- safety
- recovery

candidate writer에게 이 축을 답안처럼 강제하지 않는다.

- measurement design: `expectedDiagnosticAxes`
- 실제 system attempt 뒤: `observedDiagnosticAxes`
- validated 승격 전: 공식 `diagnosticAxes` 확정

초기 pilot 15의 한국어 자유서술형 `diagnosticAxes`는 공식 enum으로 간주하지 않는다.

### 2.3 노출 이력과 slot 적격 분리

기존 공개 후보는 다음 상태를 독립적으로 가진다.

- `public-exposed`: 이미 공개돼 future holdout으로 재사용할 수 없음
- `core-slot-qualified`: 별도 관문을 통과해 연구 포트폴리오 slot을 점유할 수 있음

공개됐다는 사실만으로 slot을 자동 배정하지 않는다.

### 2.4 private holdout

private holdout은 공식 public 100과도, 신기헌 아이데이션 연구 포트폴리오 100과도 별도다.

- 현재 holdout은 0건이다.
- 수량과 비율은 임의로 만들지 않는다.
- 기존 공개 후보를 holdout으로 되돌리지 않는다.
- access-controlled 저장소와 export 차단 장치가 준비된 뒤 새로 저작한다.
- public repo와 public site에서 holdout artifact가 발견되면 fail closed한다.

### 2.5 변경 없는 재시도 금지

동일한 category·source pool·target metadata 브리프를 그대로 반복하지 않는다. comparator의 구체 후보명과 gap 답안은 작성자에게 돌려주지 않는다. controller에는 `duplicate-heavy`, `evidence-insufficient`, `target-exhausted` 같은 추상 신호만 환류한다.

## 3. 공식 100과 신규 100의 관계

### 3.1 공식 canonical public 100

`seojoonkim/mica`에는 이미 10개 task family x 10개, 합계 100개의 canonical definition이 있다. 현재 전부 `lifecycle=candidate`이며 validated는 0건이다.

이 집합은 Simon이 관리하는 공식 public candidate catalogue다.

### 3.2 신기헌 아이데이션 100-slot 연구 포트폴리오

사용자가 반드시 완성해야 한다고 확정한 신규 100건은 공식 100을 자동 교체하지 않는다. 다음 이름과 상태로 병존한다.

- 이름: `kiheon-ideation 100-slot research portfolio`
- 구조: 공식과 같은 10개 category x 10개 slot
- 목적: 독립 자료에서 새 시나리오를 생산하고 측정 가능한 형태까지 발전시킨 대안 연구 포트폴리오
- 상태: 공식 canonical catalogue가 아님
- 효력: Simon 또는 향후 독립 결정 기구가 채택하기 전까지 공식 100을 수정하거나 대체하지 않음

따라서 100건 완성은 필수지만, 완성 뒤에도 `official replacement`나 `canonical adoption`을 주장하지 않는다. 공식 반영은 별도 governance decision이다.

## 4. 100-slot 상태 모델

각 후보와 slot은 네 축을 독립적으로 가진다.

### 축 A. 노출 이력

- `never-exposed`
- `public-exposed`

불가역 상태다. holdout 적격 판단에 사용한다.

### 축 B. 연구 후보 적격

```text
unqualified
  -> candidate-frozen
  -> comparison-cleared
  -> measurement-designed
  -> rehearsal-cleared
  -> core-slot-qualified
```

`duplicate`, `reject`, `hold`는 다음 상태로 승격하지 않는다.

### 축 C. 100-slot 점유

- `empty`
- `occupied(candidateId)`
- `blocked(evidence-insufficient)`

`occupied`만 완성 수량으로 센다. `blocked`는 다음을 뜻한다.

- 같은 브리프의 무한 반복을 중단한다.
- 근거가 현재 slot을 지지하지 않는다는 사실을 보고한다.
- 새로운 source pool이나 중립 하위영역이 생기면 다시 `empty`로 열 수 있다.
- 100건 완성 수량에는 포함하지 않는다.

프로젝트의 100건 목표는 100개 slot 전부가 `occupied`일 때만 완료다.

### 축 D. 시장·실행·공식 승격

```text
unverified
  -> market-reviewed
  -> run-eligible
  -> validated
```

이 축은 100-slot 점유와 별도다. 연구 포트폴리오 100건이 완성돼도 validated benchmark나 측정 결과가 되지는 않는다.

## 5. 세 직교 설계 항목의 최종 위치

### 5.1 `terminationClass`

후보 동결 뒤 독립 catalog annotator가 공식 enum으로 판정한다.

- `completed-final-state`
- `approval-handoff`
- `refusal`
- `escalation`

slot qualification 전 annotation과 독립 review가 필수다.

### 5.2 `declaredComplexity`

후보 동결 뒤 독립 catalog annotator가 공식 enum으로 판정한다.

- `single-step`
- `multi-step`
- `cross-session`

slot qualification 전 annotation과 독립 review가 필수다.

### 5.3 `surface`

두 필드를 분리한다.

- `targetSurface`: portfolio balancing과 batch planning에 쓰는 provisional 목표
- `confirmedSurface`: 대표 플랫폼·권한·계정·초기 상태가 사전등록된 뒤 확정하는 공식 값

`targetSurface`는 slot qualification의 planning metadata일 수 있지만 canonical `surface`가 아니다. 플랫폼이 확정되기 전에는 `confirmedSurface`를 만들지 않는다.

## 6. clean-room category-targeted authoring

### 6.1 controller가 보는 정보

- 10 x 10 slot ledger
- category별 occupied·empty·blocked 상태
- target metadata 분포
- 추상 comparator 신호

### 6.2 source researcher와 need writer가 보는 정보

- high-level category
- 중립적 하위 생활영역
- 독립 1차 자료 범위
- 시장 범위
- 필요하면 다양성 권고인 `targetSurface`, `targetTerminationClass`, `targetComplexity`

목표 세 축은 권고다. 근거가 다른 모양의 실제 부담을 지지하면 불일치를 기록하고 후보 생산을 허용한다. 목표 불일치만으로 reject하지 않는다.

### 6.3 작성자에게 금지하는 정보

- 기존 공식 100의 과제 문안
- 기존 신기헌 아이데이션 후보 본문
- 가까운 과제 ID
- 구체적인 gap 설명과 slot 정답
- comparison 판정문
- 측정 자산과 holdout 정보

후보가 동결된 뒤 comparator와 catalog annotator만 필요한 기존 자료를 연다.

## 7. v1.3.5 최소 구현 범위

다음 다섯 묶음만 `standard-v1.3.5`의 필수 구현으로 한다.

### 7.1 portfolio ledger와 annotation schema

- 10 category x 10 slot 생성
- 네 축 상태 분리
- 1 slot = 1 candidate
- 한 candidate의 중복 slot 점유 차단
- `blocked`를 완료 수량에서 제외
- 공식 canonical 100과 연구 포트폴리오 100을 별도 namespace로 유지

### 7.2 catalog annotation·review

- `terminationClass`
- `declaredComplexity`
- provisional `targetSurface`
- 독립 annotator context
- 독립 reviewer context
- frozen candidate raw-row SHA 결속

기존 54건과 신규 후보에 같은 구조를 적용한다. 기존 54건의 전수 annotation 실행은 별도 배치로 한다.

### 7.3 measurement expected diagnostics

measurement contract에 공식 enum의 `expectedDiagnosticAxes`를 추가한다. 실행 성능이나 실제 관찰을 주장하지 않는다.

### 7.4 holdout fail-closed

public export와 진행판 generator는 `taskSet=holdout` 또는 holdout artifact를 발견하면 실패해야 한다.

### 7.5 회귀 검사

- 잘못된 enum 거부
- annotation author와 reviewer 충돌 거부
- frozen candidate SHA 불일치 거부
- slot 중복 점유 거부
- `blocked`의 완료 집계 거부
- holdout public export 거부
- 동일 브리프 무변경 재시도 거부
- target metadata 불일치를 후보 reject로 오용하는 규칙 거부

## 8. v1.3.5에서 하지 않는 일

- 공식 canonical 100 수정 또는 교체
- 기존 54건 frozen row 수정
- 기존 54건 전수 annotation 실행
- private holdout 저작
- `observedDiagnosticAxes`를 실행 없이 생성
- validated promotion 수행
- std-b12 method lock 변경
- Notion·Slack·사이트·PR 외부 반영

## 9. std-b12 인수인계 경계

Claude Code는 `std-b12`를 현재 고정 revision으로 계속한다.

1. park checkpoint와 controller 세대를 먼저 확인한다.
2. comparator부터 재개한다.
3. `standard-v1.3.5` 필드나 ledger를 std-b12 산출물에 추가하지 않는다.
4. std-b12 closure에 v1.3.5 미적용 사실과 발견 결함만 기록한다.
5. std-b12가 닫힌 뒤 Codex가 v1.3.5를 구현하고 새 빈 배치를 동결한다.

## 10. Claude Code에 요청하는 다음 답변

이 문서를 읽은 Claude Code는 구현하지 말고 다음만 회신한다.

1. 판정: `ACCEPT` 또는 `MODIFY`
2. 공식 canonical 100과 연구 포트폴리오 100의 병존 정의가 명확한가
3. `targetSurface`와 `confirmedSurface` 분리가 BF-1을 해소하는가
4. `blocked`를 미완료 중간 상태로 둔 것이 100건 필수 조건과 정합하는가
5. v1.3.5 최소 구현 범위에 blocking omission이 있는가
6. std-b12의 현재 park·재개 상태

검토 결과는 새 문서에 남기고 방법·검증기·배치·사이트 파일은 수정하지 않는다.

## 11. 이후 소통 규칙

Codex와 Claude Code는 계속 다음 방식으로 소통한다.

1. 상세 판단은 `work/method-reviews/`의 자족적 인수인계 문서로 남긴다.
2. 상대 런타임에는 문서 경로와 짧은 요청 메시지만 전달한다.
3. 각 문서는 대상 문서, 근거, 판정, 수정 요청, 금지 범위, 다음 답변 형식을 포함한다.
4. 진행 중 생산 배치에는 논의 중인 method revision을 소급하지 않는다.
5. 외부 반영, commit, push는 기헌의 별도 지시 전에는 하지 않는다.
