# 한 줄 요약
MICA의 상세 계약은 평가자에게는 필요하지만 에이전트에게 그대로 공개하면 안 되며, 자연어 요청·공통 안전정책·비공개 합성 환경·비공개 평가 계약을 분리해야 실제 생활과업 수행 능력을 공정하게 측정할 수 있다.

- 작성일: 2026-08-11
- 상태: 초안
- 이 문서가 답하는 질문: 현재 MICA 후보의 상세한 측정 조건이 벤치마크 목적에 부합하는지, 에이전트에게 무엇을 공개하고 무엇을 숨겨야 하는지, `27개 후보·0회 실행`을 어떻게 해석해야 하는지 판단한다.

## 1. 독립 결론

현재처럼 최종 상태, 승인 경계, 실패 복구, 반복 가능한 초기화, 이분 판정 기준을 세밀하게 설계하는 방향 자체는 타당하다. 생활과업 벤치마크가 재현 가능하고 비교 가능한 평가가 되려면 평가자는 모호하지 않은 계약을 가져야 한다.

다만 그 계약 전체를 에이전트가 받는 요청에 넣는 것은 MICA의 목적에 맞지 않는다. 에이전트가 실제 사용자의 자연스러운 요청을 이해하고 필요한 정보를 탐색하며 안전하게 상태를 바꾸는 능력보다, 공개된 채점 규칙을 따라가는 능력을 측정하게 되기 때문이다. 상세함의 문제는 분량이 아니라 공개 위치다.

따라서 현재 설계는 폐기할 대상이 아니라, 하나의 문서처럼 보이는 내용을 공개 수준에 따라 분리할 대상이다.

## 2. 권장 공개 계층

| 계층 | 포함할 내용 | 에이전트 공개 | 이유 |
|---|---|---:|---|
| 사용자 요청 | 자연어 요청, 사용자가 알고 말해 준 조건, 실제 대화에서 합리적으로 제공될 정보 | 공개 | 실제 사용 상황의 출발점이다. |
| 공통 안전 정책 | 승인 필요 행동, 허용 도구와 금지 행동, 개인정보·비용·법적 진술 경계 | 공개 | 안전한 실행을 위해 미리 알아야 한다. |
| 합성 환경 | 계정과 서비스 상태, fixture, 실패 변형, deterministic reset, 숨은 권한 상태 | 숨김 | 환경을 미리 알면 탐색과 오류 대응 능력을 측정할 수 없다. |
| 평가 기준 | canonical final state, 금지 상태, 성공·실패·중단 oracle, readback 조건 | 숨김 | 답안과 채점 규칙 누출을 막아야 한다. 공개 카탈로그에는 요약 수준만 허용한다. |
| 채점 내부 장치 | 토큰 registry, probe, event ID, tick·비용 계산, 무결성 식별자 | 반드시 숨김 | 노출 시 벤치마크 최적화와 직접 조작이 가능하다. |

## 3. 한 후보를 세 가지 표면으로 분리한다

### 에이전트가 받는 요청

- 사용자가 실제로 말할 법한 짧은 자연어 요청
- 사용자가 알고 있는 제약과 선택
- 공통 안전·승인 정책
- 과업 수행에 사용할 수 있는 도구 범위

여기에는 성공 판정용 키, 정답 상태의 내부 필드명, 실패 변형 목록, probe, event ID를 넣지 않는다.

### 평가자가 확인하는 성공 기준

- 사용자가 원한 상태 변화가 실제로 일어났는지
- 권위 있는 기록이나 독립 readback으로 확인됐는지
- 승인 없이 넘으면 안 되는 경계를 지켰는지
- 금지 상태, 중복 실행, 허위 완료가 없는지
- 실패·중단 시 안전하게 멈추고 인계했는지

이 표면은 사람 검토자와 평가 하네스가 사용한다. 공개 과제 설명에는 이해를 돕는 요약을 보여줄 수 있지만, 실제 실행에 쓰는 완전한 oracle은 숨긴다.

### 비공개 합성 환경·채점 계약

- 초기 계정·서비스 상태와 fixture
- 성공·실패·복구 변형
- deterministic reset
- fail-closed eligibility
- canonical final state와 금지 상태
- binary oracle과 내부 probe·식별자·tick 계산

이 표면은 실행 하네스와 제한된 평가자만 사용하며 에이전트 입력과 공개 카탈로그에서 분리한다.

## 4. 상세도가 과도해지는 징후

다음 중 하나가 나타나면 평가 계약을 더 쓰기 전에 줄이거나 위치를 바꿔야 한다.

- 에이전트가 내부 필드명이나 성공 분기명을 그대로 말하면 통과할 수 있다.
- 사용자 요청만 읽고도 최종 정답 상태의 정확한 구조를 알 수 있다.
- 측정 자산이 실제 상태 변화를 확인하기보다 문구·토큰 존재 여부를 주로 확인한다.
- 사소한 구현 차이가 사용자 결과는 같아도 실패로 판정된다.
- fixture의 세부 정보가 특정 실행 경로를 사실상 지시한다.
- 평가자가 설명할 수 없는 내부 복잡도가 후보마다 누적된다.

권장 원칙은 `minimum sufficient oracle`이다. 사용자가 원한 결과, 승인 경계, 안전한 실패, 권위 있는 확인을 이분 판정하는 데 필요한 최소 정보만 채점 계약에 둔다.

## 5. 현재 후보와 다음 후보에 적용할 보완

1. 기존 후보는 삭제하지 않고 공개 필드와 비공개 필드를 분리한다.
2. 자연어 요청에는 내부 객체명, 결과 키, 실패 변형, 채점 식별자를 포함하지 않는다.
3. 평가 기준은 결과 중심으로 유지하고 특정 클릭 순서나 특정 문구를 강제하지 않는다.
4. 후보마다 `agent-visible`, `evaluator-visible`, `harness-private` 세 묶음을 독립 산출한다.
5. 검토자는 정보 누출 여부와 최소 충분성을 별도 항목으로 판정한다.
6. 새 아이디어 도출 단계에서는 상세 측정 자산을 미리 보여 주지 않고 생활 필요와 상태 변화부터 독립적으로 만든다.
7. 실제 실행 전 적어도 한 후보로 블라인드 리허설을 해, 에이전트 입력에 정답 단서가 없는지 확인한다.

## 6. `27개 후보·0회 실행`의 의미

이 숫자는 실패율이 아니라 제작 단계의 구분이다.

- `27개 후보`: 자연어 과업과 반복 가능한 합성 평가 설계가 준비된 후보 수
- `0회 실행`: 아직 비교 대상 에이전트 시스템을 하네스에 연결해 유효 실행을 수집하지 않았다는 뜻

따라서 정확도 0%, 성공률 0%, 벤치마크 완료를 뜻하지 않는다. 현재는 시험지를 만들고 검수한 단계이며, 다음 단계는 소수 후보로 실행 파이프라인과 정보 비공개 경계를 검증하는 것이다.

팀에는 `평가 시나리오 설계 27개 준비, 실제 에이전트 실행 검증은 아직 시작 전`이라고 설명하는 것이 가장 정확하다. 대시보드에서는 설계 수, 테스트한 시스템 수, 유효 실행 수, 측정 가능한 정확도·속도·비용을 별도 지표로 보여줘야 한다.

## 7. 최종 판단

방향 전환이 필요한 부분은 상세한 평가 설계를 버리는 것이 아니라, 상세 계약을 에이전트 입력과 분리하는 것이다. 이 분리를 지키면 현재의 정교함은 MICA의 재현성과 안전성을 높인다. 분리를 지키지 않으면 벤치마크가 생활과업 수행 능력보다 시험 규칙 암기와 벤치마크 최적화를 측정하게 된다.
