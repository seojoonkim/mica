# standard-v1.3.4 공정 보완안 — Claude Code 검토 의견

- 검토 대상: `work/method-reviews/2026-08-13-standard-v1.3.4-proposal.md`
- 검토자: `claude-std-b11-controller` (std-b11 생산 controller)
- 검토 시점: std-b11 `park` 완료 후 (generation 3, checkpoint 16파일 디스크 일치)
- 성격: **의견만 기록한다.** 방법 파일, 검증기, 잠금 SHA, std-b11 산출물은 수정하지 않았다.

이 검토는 std-b11을 직접 운영하며 결함을 낸 당사자의 자기 보고를 포함한다. 아래 P0·P1·P2
대부분은 검토자가 만든 실패이며, 그 실패의 재현 경로가 다음 revision의 회귀 근거가 된다.

## 1. 동의한 변경

### 1.1 `limitationsHonesty` 필수화 (제안 3.1)

동의한다. df-b11-02의 정확한 진단이다.

핵심은 검사 항목 하나를 늘리는 것이 아니라 **검증기가 exact key 집합을 강제**하는 부분이다.
std-b11에서 controller가 배치마다 source review 검사 키를 자연어로 재정의할 수 있었고, 그
과정에서 std-b9·std-b10에 있던 한계 정직성 항목이 빠졌다. 검토자가 `ev-b11-02.limitations`의
인과 서술이 원문에 없음을 확인하고도 대응하는 검사 키가 없어 `nonBlockingNotes`로만 남겼다.
계약에 키를 고정하면 이 재량 자체가 사라진다.

`limitationsHonesty`가 확인할 세 항목(원문에 없는 인과·일반화·분모 결합 / 자료가 다루지 않은
인구·시장·기간·절차 / 오래된 자료의 현재형 확정)도 std-b11에서 실제로 나온 유형과 일치한다.

### 1.2 하나라도 `fail`이면 `verdict=reject` (제안 3.1)

동의한다. 현재는 의미 판정과 기계 검증이 서로를 강제하지 않아, 검사 결과와 verdict가 어긋나도
구조 검증이 통과한다. all-pass ↔ verdict 정합성을 검증기가 보게 하는 것이 맞다.

### 1.3 controller용 `record-artifact` (제안 3.2)

동의한다. 특히 **"`defect-ledger.jsonl`을 단순 예외 처리하지 않는다"**는 판단이 옳다.

예외로 뚫으면 결함 원장만 무결성 검사 밖으로 빠진다. 그건 배치에서 가장 신뢰가 필요한 파일이고,
예외 처리는 "결함 기록은 검증 대상이 아니다"라는 잘못된 신호를 남긴다. 허용 목록 방식과
`closedBy=controllerContextId`, `timeSource=filesystem-mtime-observed-by-controller-tool` 기록,
동일 path upsert도 모두 타당하다.

### 1.4 lease TTL 180분과 역할 시작 전 잔여 확인 (제안 3.5)

동의한다. **"TTL 연장은 안전 경계를 약화하지 않는다"**는 단서가 있어 만료 후 사용자 승인 ref가
있는 `resume`만 허용하는 요건이 유지되는 점이 중요하다. TTL을 늘리는 것이 소유권 경합 방지
장치를 무르게 하는 방향으로 읽히지 않도록 이 문장을 revision 본문에도 남기는 것이 좋다.

"30분 이상 유휴가 예상되면 먼저 `park`"도 std-b11의 실제 실패(유휴 구간 만료)와 대응한다.

### 1.5 회귀 검사 10종 (제안 4)

동의한다. 특히 다음 둘이 정확하다.

- 시나리오 4·5 — 원장화 후 defect ledger 바이트가 바뀌면 resume이 실패해야 한다. 원장화가
  "한 번 기록하면 끝"이 아니라 지속적 결속임을 강제한다.
- 시나리오 10 — park·resume·controller transfer 뒤 이전 generation의 token이 실패해야 한다.
  std-b10 이중 컨트롤러 사건의 재발 방지와 직접 연결된다.

## 2. 수정 제안

### 2.1 write authorization token은 "쓰기 차단"이 아니라 "채택 차단"으로 정의할 것

제안 3.3은 token을 역할 브리핑에 포함해 쓰기 승인의 근거로 삼는다. 그러나 **역할 컨텍스트에는
그 token을 검증할 수단이 없다.** std-b11의 observation custodian이 최종 보고에서 스스로 남긴
지적이 이 한계를 정확히 보여 준다 — controller를 자칭하는 메시지의 출처를 암호학적으로
확인할 방법이 없어, 형식과 내용이 사전 예고와 일치한다는 이유로 승인으로 받아들였다는 기록이다.

따라서 token을 쓰기 시점의 예방 장치로 두면 실효는 controller의 자기 규율에 그친다.

**제안**: 검증 지점을 쓰기 시점이 아니라 **채택 시점**으로 명시한다.

- `complete-role`이 token을 검증하고, 불일치하면 산출물을 `artifactShaLedger`·`modelRecord`에
  넣지 않고 `stale-review-evidence/`로 격리한다.
- 그러면 선점 없이 작성된 산출물은 **쓰이더라도 배치에 채택되지 못한다.** 이는 역할 컨텍스트의
  협조에 의존하지 않고 controller 도구만으로 기계적으로 성립한다.
- 제안서의 `complete-role --write-authorization-token`이 이미 이 방향이므로, 3.3의 표현을
  "역할 쓰기 승인 영수증"에서 "선점 없는 산출물의 채택 차단"으로 바꾸고, 계약 문장
  "선점 전 승인 메시지는 계약상 효력이 없다"를 "선점 전 작성 산출물은 채택되지 않는다"로
  강화할 것을 제안한다.

### 2.2 역할 브리핑 기계 생성의 범위를 `roleInputAllowlist`까지 넓힐 것

제안 3.4는 exact key 목록·허용 입력·출력 path를 단일 schema에서 생성한다고 쓰여 있으나,
2절 P2의 문제 서술은 필드 개수 오기(df-b11-01)에 한정돼 있다. 필드 목록만 생성하면 df-b11-01은
막지만 더 큰 위험이 남는다.

**더 큰 위험은 허용 입력 목록이다.** controller가 브리핑에 잘못된 파일을 적으면 입력 방화벽이
그대로 뚫리고, 그 실패는 산출물 형식으로는 드러나지 않는다. 작성자에게 기존 과제·후보·comparison을
노출하지 않는다는 계약이 자연어 브리핑 한 줄에 의존하고 있다.

**제안**: `batch-manifest.json`의 `roleInputAllowlist`를 브리핑 생성기의 단일 출처로 삼고,
controller가 자연어로 입력 파일을 덧붙이거나 바꾸지 못하게 한다. 생성된 브리핑에 schema version과
allowlist 해시를 포함하면 사후 감사도 가능하다.

### 2.3 `sr-b11-02` 정정안은 제외하고 새 독립 재심만 허용할 것

제안 5절은 두 선택지를 제시한다. **첫 번째("`sr-b11-02`를 reject로 정정")는 채택하지 말 것을
제안한다.**

이는 controller가 다른 역할 컨텍스트의 판정 원문을 고쳐 쓰는 행위다. 역할 독립성 계약과
정면으로 충돌하며, std-b10 이중 컨트롤러 사건(df-b10-02)보다 나쁜 전례가 된다. 그 사건에서도
산출물 원문은 보존됐고 정정은 기록 추가로만 이뤄졌다.

**제안**: 두 번째 선택지만 남긴다 — source researcher·need writer와 다른 **새 독립 reviewer
context가 원문과 계약을 다시 대조해 별도 판정을 추가 기록**한다. 원문 `source-evidence.jsonl`과
`source-reviews.jsonl`은 수정하지 않는다. 이는 제안서 5절 말미의 원문 불변 원칙과도 일치한다.

## 3. 구현 전 확인할 기존 코드 영향

### 3.1 source review 형식이 배치마다 다르다 — exact-key 검사는 revision별 분기 필요

| 배치 | `checks` 형식 |
|---|---|
| std-b9 | **배열** — `[{item, result, evidence}, ...]` (item이 한국어 서술) |
| std-b10 | 6키 **객체** — publisher·scope·verbatim·directSupport·typeAccuracy·recency |
| std-b11 | 동일한 6키 객체 |

검증기가 7키 exact 집합을 전 배치에 강제하면 **회귀 검사에서 std-b9·std-b10이 FAIL한다.**
std-b9는 키 형식 자체가 다르고, std-b10·b11은 `limitationsHonesty`가 없다.

**필요 조치**: 새 검사는 `methodLock.revision`으로 분기해 `standard-v1.3.4` 이상에만 적용하고,
기존 배치는 각자의 lock revision 규칙으로 검증한다. std-b9 시각 파싱 규칙(v1.3.2) 때 쓴
"완료 배치에 새 규칙을 소급하지 않는다" 방식과 동일하다.

### 3.2 `closure.json` 예외와 `record-artifact` 허용 목록이 충돌한다

`_validate_recorded_artifacts`는 비어 있지 않은 모든 `.json`/`.jsonl`을 원장과 대조하되
`controller-state.json`·`batch-manifest.json`·`closure.json`을 예외로 둔다. 제안 3.2는
허용 목록을 `defect-ledger.jsonl`, `closure.json`으로 시작한다고 쓴다.

`closure.json`이 예외이면서 동시에 원장 기록 대상이 되면 두 규칙이 겹친다. 어느 쪽이
우선인지, 원장에 기록된 `closure.json`도 resume 시 대조 대상이 되는지 정해야 한다.
현재 std-b10은 closure SHA를 `artifactShaLedger`에 수동 기입했고 std-b11은 기입하지 않았다 —
두 배치의 원장 구성이 이미 다르므로 회귀 기준선도 함께 정해야 한다.

### 3.3 `complete-role`의 manifest 쓰기 스키마가 바뀐다

`complete-role`은 현재 `modelRecord`와 `artifactShaLedger`를 함께 upsert한다. token 필드를
추가하면 기존 배치의 `modelRecord` 항목과 키 구성이 달라진다. `validate-batch`가 두 형태를
모두 받아들이는지, 아니면 revision 분기가 필요한지 확인해야 한다.

### 3.4 `assign-role` 출력 형식을 소비하는 코드 확인

`assign-role`은 현재 `validate_controller_state` 결과를 `PASS batchId=... controllerStatus=...
generation=N roleClaims=N roleCompletions=N` 한 줄로 출력한다. token·`claimRecordedAt`·
`leaseExpiresAt`를 노출하면 출력 형식이 바뀐다.

**필요 조치**: 이 출력을 파싱하는 스크립트·테스트가 있는지 확인하고, 사람이 읽는 한 줄과
기계가 읽는 JSON을 분리(`--json` 플래그 등)하는 편이 안전하다. token을 평문으로 표준 출력에
노출하는 것이 적절한지도 별도 판단이 필요하다.

## 4. 추가 회귀 사례

제안 4의 10종에 더해 다음을 요청한다.

### 4.1 `active + expired` 상태의 resume — 같은 세션과 다른 세션 분기

std-b11에서 실제로 밟은 경로다. lease가 유휴 구간에 만료돼 상태는 `active`인데 시각은 만료였고,
같은 controller·같은 세션이 사용자 지시 ref와 함께 `resume`으로 복구했다(generation 2→3).

제안 4의 시나리오 4는 "승인된 resume"만 다루는데, **같은 세션이 스스로 재개하는 경우**와
**다른 세션이 인수하는 경우**는 소유권 이전 의미가 다르다. 후자만 검사하면 전자의 회귀가
빠진다. 두 분기를 모두 회귀에 넣고, 각각 generation 증가와 `controllerHistory` 기록이
올바른지 확인해야 한다.

### 4.2 실행 중인 역할이 남아 있을 때의 `park`

**현재 설계에서 복구 경로가 없는 유일한 지점이다.**

`park`는 배치 파일 전수 SHA checkpoint를 찍고 lease를 즉시 만료시킨다. 파킹 이후 역할
컨텍스트가 파일을 쓰면 checkpoint가 어긋나고, parked 상태의 `resume`은
`parked-checkpoint-mismatch`로 **하드 실패**한다. `park`는 `status == "active"`를 요구하므로
재파킹도 불가능하다. 남는 복구는 파일 삭제나 상태 파일 수동 편집뿐인데 둘 다 증거 훼손이다.

std-b11에서는 measurement asset author의 정지를 먼저 확인한 뒤 park해 이 상황을 피했으나,
그건 controller의 판단이었지 도구의 강제가 아니었다.

**요청**: `park`가 완료되지 않은 역할 선점(`roleClaims` 중 `roleCompletions`에 없는 항목)을
감지해 거절하거나 명시적 강제 플래그를 요구하도록 하고, 이를 회귀에 넣는다.

### 4.3 전건 거절과 `maxDrafts`의 상호작용

v1.3.3이 거절 원문의 같은 배치 재작성을 금지해 df-b10-03은 해소됐다. 다만 상한만큼 작성한 뒤
전건이 거절되면 배치가 0건으로 닫히는 것이 유일한 경로인지 확인이 필요하다. 0건 종결이
`closure.status="zero-accepted"`로 정상 처리되고 `validate-batch`가 통과하는지 회귀로 고정한다.

### 4.4 closure 스키마 변경 시 진행판 누락

이번 세션에서 MICA 공개 사이트의 진행판 데이터를 정본에서 생성하도록 바꿨다(생성기는 사이트
리포에 있으며 이 리포는 읽기만 한다). 생성기는 **`closure.json`의 `status`가
`completed`/`zero-accepted`일 때만** 해당 배치의 동결 후보를 진행판에 싣는다 — 파킹된 std-b11의
4건이 설계 완료로 오독되지 않게 하기 위해서다.

따라서 closure 스키마나 status enum이 바뀌면 **진행판이 조용히 배치를 누락한다.** 실패가 아니라
누락이라 눈에 띄지 않는다. closure 스키마를 바꿀 때 이 소비자를 함께 확인하도록 revision에
명시하고, 가능하면 status enum을 계약 문서에 고정할 것을 제안한다.

## 5. 보존할 std-b11 증거

다음은 v1.3.4 회귀의 실증 근거이므로 원문 그대로 보존해야 한다. 요약본으로 대체하면 회귀
fixture를 만들 수 없다.

| 증거 | 무엇을 지지하는가 |
|---|---|
| `ev-b11-02` 원문과 `sr-b11-02`의 `nonBlockingNotes` | `limitationsHonesty`의 **유일한 실증 사례**. 검토자가 "원문에 있는 것은 표2-3 각주의 특별소위원회 언급뿐"이라며 인과 서술의 부재를 특정한 문장. 분모 계열 혼재(12.3%·8.4%의 기준은 처리완료 1,060건, 앞 문장은 2,123건) 지적도 함께 |
| df-b11-03의 재현 경로 | `resume`이 `resume-artifact-unrecorded:defect-ledger.jsonl`로 차단된 실제 출력. **"결함을 성실히 기록할수록 재개가 막히는 역유인"**의 증거이며 `record-artifact`의 존재 이유 |
| df-b11-04와 승인·철회 왕복 | `assign-role` FAIL(`controller-lease-expired`)보다 쓰기 승인 메시지가 먼저 발신된 타이밍과 즉시 철회 기록. 파일은 0바이트로 미작성. **token을 예방이 아니라 채택 차단으로 설계해야 하는 근거** |
| `controller-state.json`의 generation 1→2→3 이력과 park checkpoint 16파일 | lease·resume·transfer 회귀의 실측 기준선. Codex 준비자 → Claude 승계 → 만료 후 자기 재개까지의 전 이력 |
| `ob-b11-01`의 범위 확장 | 아래 6절 참조 — observation review의 `needBoundary`가 놓친 사례 |

## 6. 제안서에서 빠진 방법론 결함 — observation review 관문

**제안서 2절은 P0을 source review에 한정하고 있으나, std-b11에서 실제로 관문이 뚫린 곳은
두 군데다.** 기헌이 생산 중단 지시에서 지적한 세 사유 중 첫 번째가 여기에 해당한다.

### 6.1 `needBoundary` — ob-b11-01의 범위 확장

`ob-b11-01`은 광고·중개 단계의 근거(공인중개사의 관리비 세부내역 표시 의무)를 **계약 기간 중
실제 관리비 부과의 부담**으로 확장했다. 근거가 지지하는 것은 계약 전 정보 표시 국면이고,
계약 기간 중 부과·정산 국면은 지지 범위 밖이다. `needBoundary` 검사가 이를 잡았어야 하나
전건 pass로 통과했다.

### 6.2 `noInventedFacts` — ob-b11-02의 인과 서술 승계

`ob-b11-02`는 source reviewer가 "원문에 없다"고 확인한 침해사고 인과 서술을 `evidenceStatus`에
포함했다. observation reviewer는 `noInventedFacts`를 pass로 판정했다. controller가 source
review의 비차단 소견을 하류에 전달하지 않고 일반 규율만 준 것이 직접 원인이지만
(자세히는 df-b11-02), 검사 자체가 상류 검토자의 지적과 대조되지 않는 구조도 원인이다.

### 6.3 요청

1. **다음 revision의 기계·의미 회귀 대상에 observation review를 포함한다.** source review와
   동일하게 exact key 집합(`evidenceAlignment`·`needBoundary`·`nonPrescription`·
   `noInventedFacts`·`stateChangeClarity`)을 계약에 고정하고, 하나라도 fail이면 reject를 강제한다.
2. **`ob-b11-01`과 `ob-b11-02`를 실제 회귀 fixture로 사용한다.**
   - `ob-b11-01` → `needBoundary=fail`이 나와야 하는 케이스
   - `ob-b11-02` → `noInventedFacts=fail`이 나와야 하는 케이스
   두 원문이 이미 배치에 보존돼 있으므로 fixture 제작 비용이 거의 없다.
3. **상류 검토자의 비차단 소견을 하류 검토자에게 전달하는 경로를 계약에 넣을지 판단한다.**
   현재는 작성자 입력 방화벽 때문에 controller가 소견을 전달하지 않고 일반 규율만 주는데,
   `nonBlockingNotes`는 작성자 금지 입력이 아니라 **검토자용 입력**이다. 하류 *검토자*에게는
   전달해도 입력 방화벽을 해치지 않으며, std-b11의 두 관문 실패를 모두 막았을 가능성이 크다.
   다만 이는 계약 변경이므로 Codex 판단에 맡긴다.

## 7. 검토 범위와 한계

- 이 문서는 제안서 본문과 std-b11 산출물·결함 원장·controller state를 근거로 작성했다.
- 검증기 코드는 `mica_batch_control.py`·`mica_batch_lifecycle.py`·`mica_batch_records.py`·
