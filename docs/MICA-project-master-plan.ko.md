# MICA 프로젝트 마스터 기획안

## Multinational Index of Consumer Agents

- 프로젝트명: **MICA**
- 정식 명칭: **Multinational Index of Consumer Agents**
- 프로젝트 유형: 다국가 소비자 에이전트 시스템 벤치마크
- 핵심 명제: **Models matter. Orchestration wins.**
- 문서 목적: MICA의 정의, 필요성, 평가 단위, 범위, 방법론, 운영 구조와 장기 발전 방향을 규정한다.

---

## 1. 프로젝트 정의

MICA는 소비자의 일상생활 속 복합적인 작업을 실제로 끝까지 수행하는 AI 에이전트 시스템을 평가하는 다국가 벤치마크다.

기존 벤치마크 다수는 기반 모델의 지식, 추론, 코딩, 도구 호출 능력을 분리된 문제로 측정한다. 그러나 소비자가 체감하는 에이전트의 품질은 모델의 단일 응답 품질만으로 결정되지 않는다.

실제 일상 태스크를 완료하려면 다음 요소가 하나의 시스템으로 작동해야 한다.

- 사용자의 의도와 제약 이해
- 적절한 모델 선택과 라우팅
- 이전 대화와 사용자 선호 기억
- 이메일, 캘린더, 브라우저, 검색, 결제, 예약 시스템 등 도구 사용
- 국가별 언어, 주소, 통화, 공휴일, 관습과 플랫폼 이해
- 사용자 승인과 안전 경계 준수
- 실패 감지, 재시도, 대안 탐색과 복구
- 완료 상태의 검증과 사용자 보고

따라서 MICA의 평가 단위는 단일 모델이 아니라 **버전이 고정된 완성형 소비자 에이전트 시스템**이다.

## 2. MICA가 필요한 이유

### 2.1 모델 성능과 실제 완료 능력의 간극

모델이 질문에 정확히 답해도 실제 예약, 일정 조정, 주문 준비, 환불 요청, 공공 서비스 신청 같은 작업은 실패할 수 있다.

대표적인 실패 원인은 다음과 같다.

- 적절한 도구를 선택하지 못함
- 로그인 상태나 페이지 흐름을 유지하지 못함
- 시간대, 주소, 통화, 언어 형식을 잘못 처리함
- 사용자 승인이 필요한 지점을 넘어감
- 중간 실패 후 부분적으로 생성된 상태를 방치함
- 완료되지 않은 작업을 완료했다고 보고함
- 국가별 주요 서비스와 채널을 지원하지 못함

MICA는 이런 시스템 수준의 차이를 결과로 드러낸다.

### 2.2 국가별 소비자 환경의 차이

동일한 태스크라도 국가가 달라지면 실행 방식이 크게 달라진다.

- 대한민국: 슈퍼앱, 본인 인증, 도로명 주소, 국내 결제 흐름
- 일본: 복잡한 입력 양식, 후리가나, 경어, 편의점 결제와 픽업
- 싱가포르: 영어 기반이지만 다문화 주소와 지역 서비스 수수료 구조
- 대만: 번체자, 메신저 기반 상거래, 편의점 물류와 전자영수증
- 태국: 태국 문자, 다양한 로마자 표기, landmark 기반 주소와 QR 결제

영어권 웹 환경에서 잘 작동하는 에이전트가 다른 국가에서도 동일하게 잘 작동한다고 볼 수 없다. MICA는 현지화를 번역 품질이 아니라 **현지 환경에서 실제 완료 상태에 도달하는 능력**으로 평가한다.

### 2.3 소비자가 원하는 것은 답변이 아니라 완료

소비자 에이전트의 핵심 가치는 다음과 같은 결과다.

- 필요한 정보를 정확히 정리함
- 제약에 맞는 선택지를 찾음
- 사용자가 검토할 수 있는 상태까지 작업을 준비함
- 안전한 승인 경계를 지킴
- 실패 시 다음 대안을 제시함
- 완료 여부를 검증함

MICA는 에이전트가 얼마나 그럴듯하게 말하는지가 아니라, **정의된 최종 상태에 얼마나 정확하고 빠르고 경제적으로 도달하는지**를 평가한다.

## 3. 프로젝트 비전

MICA의 장기 비전은 소비자 에이전트 분야에서 다음 질문에 답할 수 있는 공공 평가 인프라가 되는 것이다.

> 어떤 에이전트 시스템이 어떤 국가의 어떤 일상 태스크를 실제로 가장 잘 수행하는가?

이를 위해 MICA는 다음 원칙을 따른다.

1. 완성된 시스템을 평가한다.
2. 국가별 현실 조건을 반영한다.
3. 작업 완료 상태를 명확히 정의한다.
4. 정확성, 속도, 비용을 분리해 공개한다.
5. 안전 실패를 평균 점수 뒤에 숨기지 않는다.
6. 결과의 근거와 실행 계보를 공개한다.
7. 재현 가능한 버전과 평가 환경을 유지한다.
8. 측정하지 않은 영역을 0점이나 추정값으로 채우지 않는다.

## 4. 평가 대상

### 4.1 평가 단위

MICA의 기본 평가 단위는 다음 구성이 고정된 소비자 에이전트 시스템 스냅샷이다.

- 시스템 및 운영자
- 오케스트레이터 버전
- 사용 모델 목록과 라우팅 정책
- 메모리 방식과 보존 범위
- 사용 가능한 도구와 API
- 브라우저 제어 방식
- 검색과 정보 출처 정책
- 안전 정책과 승인 경계
- 재시도와 오류 복구 정책
- 시스템 프롬프트와 주요 설정 버전
- 평가 날짜와 실행 환경

동일한 기반 모델을 사용하더라도 오케스트레이션, 메모리, 도구, 프롬프트, 복구 정책이 다르면 별도의 시스템으로 평가한다.

### 4.2 비교 트랙

#### Full Agent Track

실제 제품에 가까운 완성형 에이전트 시스템을 비교한다. 모델, 도구, 메모리, 라우팅을 각 시스템이 자유롭게 구성한다.

#### Controlled Model Track

동일한 기반 모델 또는 제한된 모델 집합을 사용하게 하고 오케스트레이션과 도구 사용의 차이를 비교한다.

#### Controlled Tools Track

동일한 도구 접근 권한을 제공하고 시스템의 계획, 라우팅, 메모리와 복구 능력을 비교한다.

#### Open System Track

공개된 코드와 설정으로 재현 가능한 시스템을 평가한다.

#### Commercial System Track

공개 제품이나 상용 API를 평가하되, 버전과 실행 조건을 최대한 고정하고 재검증 가능성을 확보한다.

## 5. 초기 국가 범위

MICA의 초기 벤치마크 국가는 다음 5개 시장이다.

1. 대한민국
2. 일본
3. 싱가포르
4. 대만
5. 태국

### 국가 선정 기준

- 일상 디지털 서비스가 충분히 발달했는가
- 언어와 문자 체계가 서로 다른가
- 주소, 결제, 예약, 물류 체계가 구별되는가
- 글로벌 에이전트가 현지화 실패를 보일 가능성이 있는가
- controlled 또는 sandbox 평가 환경을 구성할 수 있는가
- 국가 간 비교가 오케스트레이션과 현지화 능력을 진단하는 데 유의미한가

### 국가 확장 원칙

추후 국가는 지역 대표성만으로 추가하지 않는다. 태스크 환경, 평가 파트너, controlled account, 데이터 관리, 현지 검수 역량이 확보된 경우에만 edition에 포함한다.

## 6. 평가 카테고리

MICA의 평가 taxonomy는 소비자의 일상생활 전반을 다음 10개 카테고리로 구분한다.

### 6.1 Email & Calendar

**이메일·캘린더**

- 이메일 확인과 요약
- 답장 초안과 발송 준비
- 일정 생성, 변경, 삭제
- 다자간 일정 조율
- 시간대와 공휴일 처리
- 기존 약속과 메시지 간 일관성 유지

핵심 평가 질문:

- 에이전트가 메시지 속 약속과 제약을 정확히 추출하는가
- 일정과 답장의 내용이 서로 일치하는가
- 국가와 관계에 맞는 언어 register를 사용하는가
- 외부 발송 전에 승인 경계를 지키는가

### 6.2 Shopping & Delivery

**쇼핑·배송**

- 조건 기반 상품 탐색
- 가격, 수수료, 배송비 비교
- 장바구니 구성
- 품절과 대체 상품 처리
- 현지 주소와 픽업 방식 처리
- 주문과 결제 직전 상태 준비

핵심 평가 질문:

- 숨겨진 비용까지 포함해 예산을 지키는가
- 현지 물류와 주소 형식을 처리하는가
- 사용자의 대체 규칙을 지키는가
- 승인 없이 주문이나 결제를 실행하지 않는가

### 6.3 Travel Planning & Accommodation

**여행 계획·숙박**

- 다구간 여행 일정 수립
- 교통과 숙소 탐색
- 날짜, 예산, 수하물, 접근성 제약 반영
- 실제 예약 가능한 재고 확인
- 취소나 지연 발생 시 재계획

핵심 평가 질문:

- 그럴듯한 일정이 아니라 실제 선택 가능한 옵션을 제시하는가
- 국가별 판매 채널과 공개 시점을 반영하는가
- 전체 비용과 제약 충족 여부를 명확히 설명하는가

### 6.4 Dining & Reservations

**식당·예약**

- 식당과 지역 서비스 탐색
- 인원, 시간, 식이 조건 반영
- 식당과 호텔, 시설 예약 준비
- 전화, 메신저, 카드 홀드 등 특수 채널 처리
- 완료 불가능한 경우 정확히 중단하고 인계

핵심 평가 질문:

- 예약 가능성과 조건을 실제 근거로 확인하는가
- 전화나 본인 인증이 필요한 경우 완료를 가장하지 않는가
- 비가역 조치 전에 사용자에게 인계하는가

### 6.5 Money, Banking & Investing

**금융·은행·투자**

- 계좌와 카드 내역 확인
- 지출과 수수료 요약
- 환율, 예금, 금융상품 비교
- 포트폴리오와 위험 노출 요약
- ETF와 펀드 탐색 및 비교
- 배당과 세금 문서 정리
- 투자 주문서 작성과 승인 직전 검증

핵심 평가 질문:

- 최신 가격, 수수료, 환율과 위험 정보를 정확히 공개하는가
- 수익을 보장하거나 적합성을 근거 없이 추정하지 않는가
- 합성 포트폴리오와 controlled account만 사용하는가
- 송금, 매수, 매도, 계좌 개설 전에 명시적 최종 승인을 요구하는가

### 6.6 Mobility & Local Transit

**이동·대중교통**

- 도어 투 도어 경로 계획
- 막차와 환승 조건 처리
- 교통비와 소요 시간 계산
- 접근 가능한 이동 경로 확인
- 현지 교통카드와 승차 규칙 반영
- 승차 호출과 결제 직전 준비

핵심 평가 질문:

- 실제 출발 시점의 운행 정보를 반영하는가
- 환승, 요금, 접근성 정보를 검증하는가
- 이동 수단이 끊긴 경우 현실적인 대안을 제시하는가

### 6.7 Healthcare Administration

**의료 행정**

- 진료 예약
- 의뢰서와 기록 요청 준비
- 보험 청구 서류 정리
- 필요한 신분증과 문서 확인
- 비용과 행정 절차 안내

범위 제한:

- 진단하지 않는다.
- 치료법을 추천하지 않는다.
- 의료 전문가를 대체하지 않는다.
- 민감한 건강정보를 승인 없이 전송하지 않는다.

### 6.8 Government & Civic Services

**정부·공공 서비스**

- 자격 조건 확인
- 공식 출처와 최신 양식 확인
- 필요 문서 체크리스트 작성
- 신청서와 민원 초안 작성
- 공공기관 방문 예약
- 마감일과 법적 효력 확인

범위 제한:

- 불확실한 자격을 확정적으로 주장하지 않는다.
- 법적 효력이 있는 제출은 명시적 승인 없이 실행하지 않는다.
- identity credential을 임의로 사용하지 않는다.

### 6.9 Home & Utilities

**주거·공과금**

- 전기, 수도, 가스, 관리비 확인
- 청구 이상 분석
- 요금제 비교
- 입주와 퇴거에 따른 서비스 이전
- 수리 문의와 견적 준비
- 해지, 단전, 계약 변경 준비

핵심 평가 질문:

- 실제 사용량과 계약 조건을 근거로 비교하는가
- notice period와 위약금을 반영하는가
- 비가역적인 해지나 단전 전에 승인을 받는가

### 6.10 Telecom & Digital Subscriptions

**통신·디지털 구독**

- 휴대폰과 인터넷 요금제 비교
- 로밍과 eSIM 준비
- 데이터 사용량과 청구 확인
- 중복 구독과 무료 체험 탐지
- 구독 해지 준비
- 부당 청구 이의제기 초안
- 번호이동과 위약금 확인

1번 카테고리와의 구분:

- Email & Calendar는 사람과 약속에 대한 커뮤니케이션 실행을 평가한다.
- Telecom & Digital Subscriptions는 통신사와 디지털 서비스 계정의 가입, 변경, 청구, 해지 생애주기를 평가한다.

## 7. 태스크 설계 구조

각 평가 태스크는 최소한 다음 항목을 포함한다.

### Task ID

국가, 카테고리, 버전과 시나리오를 식별하는 고유 ID다.

### Synthetic Persona

태스크에 필요한 일정, 예산, 주소, 선호, 계정 상태를 가진 합성 사용자다. 실제 개인 데이터를 사용하지 않는다.

### Starting State

평가 시작 시점의 이메일, 캘린더, 장바구니, 예약 상태, 계정 정보, 문서와 브라우저 상태를 정의한다.

### User Request

소비자가 실제로 사용할 법한 자연어 요청이다. 필요한 정보가 모두 명시되지 않을 수 있으며, 에이전트가 적절한 확인 질문이나 추론 경계를 판단해야 한다.

### Constraints

예산, 시간, 위치, 식이 조건, 접근성, 승인 권한, 개인정보 범위와 같은 조건이다.

### Canonical Final State

성공으로 인정되는 최종 상태를 기계 검증 가능한 형태로 정의한다.

예시:

- 일정이 올바른 시간대로 생성됨
- 답장 초안과 일정 내용이 일치함
- 장바구니 총액이 모든 수수료를 포함해 예산 이하임
- 예약 가능한 옵션과 근거가 제시됨
- 사용자 승인 전 결제는 실행되지 않음

### Confirmation Boundary

에이전트가 사용자 승인 없이 넘어가면 안 되는 경계다.

예시:

- 이메일 발송
- 결제와 주문 확정
- 예약 확정과 카드 홀드
- 송금, 매수, 매도
- 법적 효력이 있는 정부 제출
- 민감한 건강정보 전송
- 서비스 해지와 번호이동

### Failure and Recovery Events

품절, 인증 요청, 페이지 구조 변경, API 오류, 일정 충돌, 결제 거부와 같은 복구 시나리오를 정의한다.

### Evidence Requirements

최종 상태뿐 아니라 다음 근거를 남긴다.

- 사용한 도구와 주요 호출
- 외부 출처와 timestamp
- 사용자 승인 기록
- 오류와 재시도
- 최종 상태 검증 결과
- 비용과 실행 시간

---

## 8. 평가 환경과 트랙

### 8.1 Simulator Track

완전히 통제된 합성 서비스와 fixture를 사용한다.

장점:

- 반복성과 재현성이 높음
- 실제 결제나 예약 피해가 없음
- 오류 시나리오를 안정적으로 주입 가능

한계:

- 실제 웹사이트와 플랫폼의 복잡성을 모두 반영하지 못함

### 8.2 Live Shadow Track

실제 서비스나 최신 웹 환경을 탐색하지만 비가역적인 작업은 실행하지 않는다.

예시:

- 실제 상품과 가격 탐색
- 예약 가능 여부 확인
- 주문서나 예약서 작성
- 결제와 확정 직전 중단

### 8.3 Verified Live Track

파트너가 제공하는 controlled inventory, sandbox payment, test account를 사용해 제한적으로 실제 완료를 검증한다.

요건:

- 명확한 법적, 안전, 데이터 처리 계약
- 평가 전용 계정과 재고
- 실제 사용자나 상점에 피해가 없는 구조
- 비가역 작업에 대한 별도 승인과 감사 로그

---

## 9. 핵심 결과 지표

MICA는 Accuracy, Speed, Cost를 하나의 종합점수로 합치지 않는다.

### 9.1 Accuracy

정의된 최종 상태에 도달한 eligible run의 비율이다.

성공 조건은 다음을 모두 포함한다.

- 최종 상태 충족
- 필수 제약 충족
- 확인 경계 준수
- 치명적 안전사고 없음
- 완료 여부의 정직한 보고

표시 항목:

- 성공률
- eligible run 수
- 성공 run 수
- Wilson 95% confidence interval
- 태스크 coverage

### 9.2 Speed

성공한 eligible run의 end-to-end wall-clock time을 측정한다.

표시 항목:

- p50
- p95
- 성공 run 수
- timeout과 failure population의 별도 공개

실패를 빠르게 반환한 시스템이 빠른 성공처럼 보이지 않도록 실패 run은 성공 latency 통계에서 제외한다.

### 9.3 Cost

모든 eligible attempt 비용을 성공 run 수로 나눈 cost per success를 사용한다.

포함 비용:

- 모델 token 비용
- subagent 호출
- 검색과 브라우저 실행
- 유료 API와 도구
- 실패 후 재시도

이 구조는 실패 비용을 숨기지 않는다.

### 9.4 Safety

Safety는 평균 성능 속에 숨기지 않고 별도 gate와 사건 수로 공개한다.

대표 사건:

- 승인 없는 결제나 발송
- 개인정보의 잘못된 전송
- 법적 효력이 있는 무단 제출
- 금융 거래의 무단 실행
- 허위 완료 보고
- 존재하지 않는 근거 생성
- 의료 진단이나 투자 수익 보장

치명적 안전사고가 발생한 run은 성공으로 인정하지 않는다. edition 정책에 따라 시스템 전체의 publication eligibility를 차단할 수 있다.

## 10. 진단 지표

외부 결과 지표와 별도로, 실패 원인을 분석하기 위한 진단축을 운영한다.

- Orchestration
- Model Routing
- Memory
- Tool/API Use
- Browser Control
- Localization
- Safety
- Recovery

초기 단계에서는 근거 없는 1점부터 5점의 주관적 점수를 부여하지 않는다. 각 진단축은 evidence-led 방식으로 다음을 공개한다.

- 관찰된 행동
- 성공과 실패 사례
- 관련 run 수
- 재현 가능한 증거
- 판단 한계

## 11. 국가별 집계와 글로벌 결과

### 국가 우선 원칙

모든 결과는 국가별로 먼저 계산한다.

이유:

- 통화가 다름
- 서비스와 도구가 다름
- 언어와 주소 체계가 다름
- 국가별 run 수가 다를 수 있음
- 동일 태스크 이름도 실제 난이도가 다름

### 글로벌 정확도

각 시스템의 국가별 Accuracy를 동일 가중 평균한다.

- 각 국가가 동일한 비중을 가짐
- run 수가 많은 국가가 글로벌 결과를 지배하지 않음
- 한 국가의 coverage가 없으면 글로벌 수치를 추정하지 않고 withheld 처리 가능

### 글로벌 Speed와 Cost

초기 edition에서는 단일 글로벌 Speed와 Cost를 제공하지 않는다.

- 국가별 latency 환경이 다름
- 통화가 다름
- API와 서비스 가격이 다름
- 구매력 조정이나 환율 변환이 비교를 왜곡할 수 있음

필요한 경우 별도의 정규화 연구를 거친 후 보조 지표로만 제공한다.

---

## 12. 검증 상태

각 결과에는 다음 검증 상태를 부여한다.

### Independent Rerun

MICA 운영자가 동일 시스템 스냅샷을 독립적으로 재실행한 결과다.

### Provisional

일부 재실행과 증거 검토를 마쳤지만 완전한 검증이 완료되지 않은 결과다.

### Self Reported

시스템 운영자가 제출한 결과로 독립 재검증이 완료되지 않았다.

공식 leaderboard의 기본 보기는 Independent Rerun만 포함한다.

---

## 13. 결과 공개 구조

각 공개 결과는 최소한 다음 계층으로 구성한다.

### Country View

국가별 시스템 성능과 현지 환경의 특수성을 보여준다.

### Task Family View

10개 카테고리별 성공률, 속도, 비용과 대표 실패 유형을 보여준다.

### System View

특정 에이전트 시스템의 구성, 지원 국가, 강점, 약점과 실행 근거를 보여준다.

### Evidence View

system × country × task family 단위의 run cell과 근거 계보를 공개한다.

### Methodology View

태스크 설계, scoring, eligibility, safety gate, confidence interval과 publication policy를 설명한다.

---

## 14. 데이터와 근거 계보

### Canonical Run Cell

기본 데이터 단위는 다음 조합이다.

`System × Country × Task Family × Edition`

각 run cell은 다음 정보를 포함한다.

- eligible run 수
- successful run 수
- task coverage
- 성공 latency 기록
- 전체 eligible attempt latency
- 총 eligible cost
- critical safety events
- verification status
- data status
- publication eligibility
- evidence references

### 불변성과 버전

- 공식 edition 데이터는 수정하지 않는다.
- 오류 수정은 correction record로 남긴다.
- 시스템 스냅샷과 평가 환경 버전을 공개한다.
- 원본 evidence와 파생 결과를 분리한다.
- 파생 테이블은 canonical run cell에서 재계산 가능해야 한다.

### 데이터 정직성

현재 프로젝트의 평가 taxonomy는 10개 카테고리지만 게시된 result coverage는 0개다.

10개 카테고리 모두 taxonomy와 태스크 정의는 존재하지만 아직 게시할 수 있는 결과를 측정하지 않았다.

- 가짜 run cell을 만들지 않는다.
- 결과가 없으면 0점이 아니라 `Not measured`로 표시한다.
- taxonomy 범위와 실제 결과 coverage를 항상 함께 공개한다.

---

## 15. Publication Policy

공식 결과로 공개하려면 다음 조건을 충족해야 한다.

- 최소 run 수
- 필수 태스크 coverage
- 독립 재실행
- 치명적 안전사고 기준 충족
- 비용과 latency 기록 완전성
- 시스템 스냅샷 고정
- evidence audit 통과
- evaluator와 환경 버전 공개

threshold가 아직 확정되지 않은 단계에서는 publication eligible 판정을 만들지 않는다.

Demo와 preview 데이터는 항상 다음 상태를 유지한다.

- `dataStatus: demo` 또는 `preview`
- `publicationEligible: false`
- `Illustrative demo data`
- `Not an official ranking`

## 16. 운영 구조

### Benchmark Council

방법론, edition 범위, publication policy와 주요 변경을 승인한다.

### Country Leads

국가별 태스크 현실성, 언어, 서비스 환경, 안전 경계를 검수한다.

### Evaluator Operations

시스템 등록, 환경 구성, run 실행, 오류 처리와 evidence 수집을 담당한다.

### Independent Review

결과, 계산, publication eligibility와 이해충돌을 검토한다.

### System Operators

평가 대상 시스템의 정확한 구성과 실행 조건을 제출하고, 재실행을 위한 접근 방법을 제공한다.

### Appeals Process

시스템 운영자가 결과나 평가 환경에 이의를 제기할 수 있도록 versioned appeal과 correction 절차를 운영한다.

## 17. 이해충돌과 공정성

- 스폰서 여부가 결과나 평가 조건에 영향을 주지 않도록 한다.
- 평가 비용 지원과 결과 판단을 분리한다.
- evaluator가 특정 시스템과 이해관계가 있으면 공개하고 해당 판단에서 제외한다.
- 시스템별 도구 제한과 실행 조건을 투명하게 공개한다.
- 태스크 유출과 benchmark gaming을 줄이기 위해 공개 태스크와 비공개 변형 태스크를 혼합한다.
- edition 사이에 태스크와 환경을 점진적으로 교체한다.

## 19. MICA가 제공할 연구 가치

### 시스템 비교

같은 모델을 사용한 서로 다른 에이전트가 왜 다른 결과를 내는지 분석할 수 있다.

### 모델 라우팅 연구

태스크 유형별 자동 모델 선택이 정확도, 속도, 비용에 미치는 영향을 측정할 수 있다.

### 메모리 연구

사용자 선호와 이전 약속을 기억하는 능력이 장기 태스크 완료에 미치는 영향을 평가할 수 있다.

### 도구와 API 연구

브라우저 중심 시스템과 API 중심 시스템의 성공률과 복구력을 비교할 수 있다.

### 현지화 연구

언어 번역을 넘어 주소, 결제, 플랫폼, 관습, 행정 규칙을 처리하는 능력을 비교할 수 있다.

### 안전과 승인 연구

에이전트가 언제 자율적으로 진행하고 언제 사용자에게 인계해야 하는지 실제 태스크 단위로 분석할 수 있다.

### 비용 효율성 연구

더 많은 모델과 도구를 사용하는 시스템이 실제 성공당 비용에서도 우수한지 검증할 수 있다.

## 20. 주요 사용자

### 소비자

자신의 국가와 태스크에서 실제로 잘 작동하는 에이전트를 확인한다.

### 에이전트 개발사

제품의 국가별 약점, 도구 실패, 복구 문제와 비용 구조를 진단한다.

### 모델 제공사

기반 모델이 실제 에이전트 시스템 안에서 어떤 병목을 만드는지 확인한다.

### 플랫폼과 API 사업자

에이전트가 자사 서비스를 안정적으로 사용할 수 있는지 평가한다.

### 연구자

오케스트레이션, 라우팅, 메모리, 현지화와 안전을 재현 가능한 데이터로 연구한다.

### 정책기관과 소비자 보호 조직

에이전트의 자율 실행, 책임, 허위 완료와 고위험 행동을 관찰한다.

## 21. MVP와 단계별 로드맵

### Phase 0: Public Preview

목표:

- 프로젝트 정의와 방법론 공개
- 5개국 구조 공개
- 10개 taxonomy 공개
- illustrative fixture로 데이터 인터페이스 검증
- publication guard와 evidence 구조 검증

현재 상태:

- 5개국
- 10개 taxonomy
- 게시된 result family 0개 (system registry와 run cell 모두 비어 있음)
- 공식 결과 아님

### Phase 1: Task Specification

목표:

- 5개국 × 10개 카테고리의 domain matrix 완성
- 국가별 canonical task 작성
- final state와 confirmation boundary 검수
- simulator 환경과 evaluator 구현

### Phase 2: Pilot Evaluation

목표:

- 최대 5개 시스템 평가
- simulator와 live shadow 병행
- independent rerun 운영
- scoring과 publication threshold 검증
- country lead 검수

## 23. 성공 기준

MICA 프로젝트는 다음 조건을 충족할 때 의미 있는 벤치마크로 자리 잡았다고 판단한다.

### 측정 신뢰성

- 동일 시스템 재실행 시 허용 범위 내 결과 재현
- 태스크 성공 판정의 evaluator 간 일치
- 모든 공개 수치의 run cell 역추적 가능

### 시장 현실성

- country lead가 태스크와 final state를 실제적인 것으로 검수
- 국가별 주요 플랫폼, 주소, 통화와 서비스 흐름 반영
- 번역 문제가 아니라 현지 실행 능력의 차이를 측정

### 시스템 진단력

- 단순 순위뿐 아니라 실패 원인을 오케스트레이션, 라우팅, 메모리, 도구, 현지화, 안전, 복구로 설명 가능

### 공공 신뢰

- demo와 공식 결과의 구분이 명확함
- 이해충돌과 correction 기록 공개
- 측정하지 않은 결과를 추정하지 않음
- 치명적 안전 실패를 숨기지 않음

### 산업 활용성

- 개발사가 다음 버전의 개선 우선순위를 도출할 수 있음
- 소비자가 국가와 태스크에 맞는 시스템을 비교할 수 있음
- 연구자가 데이터를 재현하고 확장할 수 있음

## 25. 최종 원칙

MICA는 가장 말이 유창한 에이전트를 찾는 프로젝트가 아니다.

MICA는 서로 다른 국가의 실제 생활 환경에서 사용자의 의도를 이해하고, 적절한 모델과 도구를 선택하고, 안전한 경계를 지키며, 실패를 복구하고, 정의된 최종 상태를 검증 가능한 방식으로 달성하는 에이전트 시스템을 찾는 프로젝트다.

MICA의 가치는 하나의 순위표보다 다음에 있다.

- 어떤 시스템이 실제로 완료하는가
- 어느 국가와 태스크에서 강하거나 약한가
- 왜 성공하거나 실패하는가
- 얼마나 빠르고 경제적인가
- 사용자의 권한과 안전을 지키는가
- 동일 결과를 다시 재현할 수 있는가

이 원칙을 유지할 때 MICA는 소비자 에이전트 산업을 위한 신뢰 가능한 글로벌 평가 기반이 될 수 있다.
